## 1. 전체 아키텍처

### 1.1 서비스 구성

| 서비스 | 포트 | 역할 | 자기 DB |
|---|---|---|---|
| discovery-service | 8761 | Eureka Server — 서비스 등록/탐색 | 없음 |
| api-gateway | 8080 | Spring Cloud Gateway(MVC/서블릿) — 단일 진입점, 순수 라우팅 | 없음 |
| auth-service | 8081 | 로그인, JWT 발급, OTP(관리자 2차 인증), 비밀번호 재설정 | `gyubot_auth` |
| user-service | 8082 | 마이페이지, 회원/관리자 계정 관리, 가입 승인 | `gyubot_user` |
| document-service | 8083 | 문서 업로드(S3/MinIO), 버전 메타데이터 | `gyubot_document` |
| search-service | 8084 | 문서 Chunking, 임베딩, Elasticsearch 하이브리드 검색 | 없음(ES에 저장) |
| chat-service | 8085 | RAG 질의응답, 대화 이력, 근거(citation) 저장 | `gyubot_chat` |
| frontend | 5173(dev) | Vue 3 SPA — 임직원 화면 + 관리자 콘솔 | - |

database-per-service 원칙을 지켜서 서비스마다 자기 DB만 갖고, 다른 서비스 데이터가 필요하면 반드시 그 서비스의
API(내부 API 포함)를 호출한다. 서비스 간 직접 DB 접근은 어디에도 없다.

### 1.2 인프라 (`infra/docker-compose.yml`)

MariaDB(:3306), Redis(:6379), Mailpit(SMTP :1025 / 웹 UI :8025), Kafka(:9092, KRaft 단일 노드),
MinIO(S3 호환, API :9100 / 콘솔 :9101), Elasticsearch(:9200, 단일 노드, 로컬 전용 무인증),
Ollama(:11434, LLM/임베딩 로컬 추론). 전부 로컬 컨테이너라 사용량 과금이 없다.

### 1.3 데이터 흐름 두 가지

**문서 색인 (관리자가 문서 등록할 때, 비동기)**
```
관리자 업로드 → document-service: S3(MinIO) 저장 + DB 기록 + Kafka "document.uploaded" 발행
             → search-service: 이벤트 구독 → 원본 다운로드(내부 API) → PDFBox 텍스트 추출
             → 800자 단위 청크 분할(100자 겹침) → Ollama(nomic-embed-text)로 각 청크 임베딩
             → Elasticsearch에 벡터+원문 함께 색인
```

**질의응답 (임직원이 챗봇에 물어볼 때, 동기)**
```
사용자 질문 → chat-service: 메시지 저장 → search-service "/internal/search" 호출
           → search-service: 질문도 임베딩 → ES에서 BM25(키워드) + kNN(벡터) 각각 검색 → RRF로 병합해 top-5 반환
           → chat-service: 청크들을 시스템 프롬프트에 삽입 → Ollama(qwen2.5:7b)로 답변 생성
           → 답변 + 근거(answer_source) 저장 → 프론트에 반환(근거 문서 카드 클릭 시 상세는 별도 API)
```

핵심: **검색은 벡터+키워드 하이브리드, 답변 생성만 LLM이 담당**. 이전 대화 맥락은 LLM에 넘기지 않고 매 턴 새로
검색하는 구조(stateless RAG) — 그래서 후속 질문도 관련 규정을 다시 찾아서 답한다.

### 1.4 인증/인가 구조

- JWT는 **auth-service만 발급**, 나머지 서비스(user/document/chat)는 같은 `app.jwt.secret`/`issuer`로 **검증만** 한다.
- httpOnly 쿠키(`ACCESS_TOKEN`) + Redis 기반 `REFRESH_TOKEN`(회전).
- 서비스 간 호출(예: user-service → auth-service 비밀번호 변경)은 JWT가 아니라 양쪽이 공유하는
  `X-Internal-Token` 헤더로 보호하는 `/internal/**` 엔드포인트를 쓴다. 최종 사용자는 이 경로를 직접 호출할 수 없다
  (게이트웨이에도 라우트를 만들지 않음).
- 역할: `EMPLOYEE` / `ADMIN` / `SUPER_ADMIN`. `SUPER_ADMIN`은 `ROLE_ADMIN`+`ROLE_SUPER_ADMIN`을 동시에 부여받아
  기존 `hasRole("ADMIN")` 규칙을 안 건드리고도 관리자 기능을 그대로 쓴다.
- 멀티테넌트: 모든 조회성 API가 요청자의 `companyId`로 필터링한다. 다른 회사 데이터는 403이 아니라 **404**로
  존재 자체를 숨긴다(권한 문제가 아니라 "테넌트 격리" 정책).

## 2. 서비스별 구현 요약

### discovery-service / api-gateway
- Eureka로 서비스 등록/탐색, 게이트웨이는 `application.yml`에 명시적 라우트만 두고(`/api/auth/**`,
  `/api/users/**`, `/api/documents/**`, `/api/chat/**`, `/api/companies/**`) **discovery locator는 껐다**
  (자동 라우트 생성을 켜두면 `X-Internal-Token`만으로 보호되던 내부 API가 그대로 외부에 노출될 뻔했음).
- search-service는 아예 공개 라우트가 없다 — 내부 전용이라 게이트웨이로 노출할 이유가 없음.

### auth-service
- 로그인(EMPLOYEE 즉시 발급 / ADMIN은 OTP 2차 인증 후 발급), refresh 토큰 회전, 비밀번호 재설정, 로그아웃.
- 멀티테넌트 `company` 테이블(SUPER_ADMIN 전용 관리) 보유.
- `DevDataSeeder`로 로컬 테스트 계정 자동 생성(`employee@gyubot.local` / `admin@gyubot.local`, `Passw0rd!`).

### user-service
- 마이페이지, 관리자용 회원/관리자 계정 관리, 가입 승인(예외 가입) 플로우.
- 비밀번호 변경은 본인 확인만 여기서 하고 실제 변경은 auth-service에 내부 API로 위임(자격정보는 auth-service DB에만 있음).

### document-service
- 업로드(50MB 제한, PDF/HWP 확장자 검증) → MinIO 저장 → DB 기록 → Kafka 이벤트 발행까지 원자적으로 처리.
- 버전 메타데이터(`version`/`category`/`effectiveDate`/`revisionDate`), 상태(`ACTIVE`/`UPCOMING`)는 저장하지
  않고 매번 오늘 날짜와 비교해 계산(드리프트 방지).
- 다운로드는 임직원에게도 열려 있음(챗봇 "원문 확인" 기능 때문) — 대신 companyId 일치 여부를 반드시 확인.

### search-service
- Kafka 이벤트 구독 → PDFBox 텍스트 추출 → Chunking → Ollama 임베딩 → ES 색인까지 전부 비동기 파이프라인.
- 벡터 DB를 따로 두지 않고 **Elasticsearch 하나**로 BM25+kNN 하이브리드 검색(RRF는 ES API 대신 직접 구현).
- HWP는 아직 텍스트 추출을 지원하지 않음(성숙한 자바 HWP 파서가 마땅치 않음) — 원본 저장은 되지만 검색 대상에서 빠짐.

### chat-service
- 질문 → 검색(top-5) → 프롬프트 조립 → Ollama 답변 생성 → 답변+근거 저장까지의 RAG 루프.
- 검색 결과가 0건이면 LLM을 아예 호출하지 않고 고정 안내 문구 반환(불필요한 추론 방지).
- 대화방 소유권 검증 실패 시 403이 아니라 404(테넌트 격리 정책 일관 적용).

### frontend
- Vue 3 + Vite + Pinia + vue-router + element-plus + axios.
- 임직원 화면(`EmployeeShell`)과 관리자 콘솔(`AdminShell`, SUPER_ADMIN 전용 메뉴 별도)을 라우터 메타로 완전히 분리.
- 개발 서버는 `/api/*` 전체를 api-gateway(:8080) 하나로만 프록시 — 프론트가 서비스별 포트를 알 필요 없음.

## 4. 트러블슈팅 모음

실제로 겪고 해결한 문제들. "증상 → 원인 → 해결 → 다음에 의심할 순서"로 정리.

### 4.0 근거 문서가 관련 없어도 항상 전부(top-K) 표시됨 (search-service, 2026-08-27)
- **증상**: 테스트용 규정 문서 4개(휴가/지급결의/물품구매/결재선)를 넣고 질의했더니, 완전히 무관한 질문("화성 여행 경비는?")에도 인덱스에 있는 문서 5개가 전부 근거로 붙어 나옴.
- **원인 조사**: `/internal/search`를 직접 호출해 BM25/kNN 두 branch를 분리해서 확인 — BM25는 무관한 질문에 정확히 0건을 반환(정상)했지만, **kNN은 실제 유사도와 무관하게 topK를 항상 채워서 반환**하는 ES kNN의 기본 동작 때문에 매번 5개 전부가 벡터 branch에서 딸려 들어왔음. 더 깊이 파보니 이 코퍼스(짧고 문체가 비슷한 사내 규정 문서들)에서는 nomic-embed-text의 원시 코사인 유사도가 관련 있는 질문과 없는 질문을 사실상 구분하지 못했다(오히려 무관한 질문이 관련 질문보다 유사도가 더 높게 나온 경우도 있었음) — 그래서 벡터 유사도에 최소 임계값(threshold)을 거는 방식은 애초에 통하지 않는다는 걸 직접 점수를 찍어보고 확인.
- **해결**: `HybridSearchService.search()`를 두 가지로 고침 — (1) 키워드(BM25) branch가 0건이면 벡터 branch를 아예 안 쓰고 즉시 빈 결과 반환, (2) 키워드 branch가 결과를 찾았을 때도, 벡터 branch는 그 결과의 "순위 보정(re-rank)"에만 쓰고 벡터 단독으로 새 청크를 결과에 끼워 넣지 못하게 필터링. 벡터 branch의 RRF 가중치도 키워드 대비 낮춰서(1.0 vs 0.3), 특정 문서(원인 불명의 임베딩 공간 쏠림으로 거의 모든 질문에서 벡터 순위가 높게 나오던 문서)가 실제로 더 정확한 키워드 매칭 결과를 순위에서 밀어내는 것도 막음.
- **트레이드오프**: 이전에 "자랑거리"로 검증했던 "키워드 겹침이 전혀 없는 한국어-영어 교차 언어 순수 벡터 매칭" 사례는, 이번 재검증에서 그 문서가 오히려 모든 질문에 대해 가장 낮은 유사도로 나와 사실은 코퍼스에 경쟁 문서가 적어서 우연히 1등이었던 것으로 재해석됨 — 이 임베딩 설정으로는 순수 의미 기반 매칭이 이 정도 규모/성격의 코퍼스에서 안정적으로 동작한다고 보기 어렵다는 결론. 키워드가 하나도 안 겹치는 순수 패러프레이즈 질문은 이제 결과 없음으로 처리될 가능성이 높아짐 — 검색 recall보다 precision(잘못된 근거를 안 보여주는 것)을 우선한 의도적 선택.
- **남은 한계**: 이 코퍼스는 형태소 분석기(Nori) 없이 표준 analyzer를 쓰고 있어, 조사가 붙은 짧은 한글 단어가 우연히 다른 단어와 토큰이 겹치는 오탐이 여전히 가능함 — 실제로 "300만원짜리 지출은 누가 결재해야 해?" 질문에서 질문의 "해야"가 휴가 규정의 "다음 **해**"(연도를 뜻하는 "해")와 우연히 토큰이 겹쳐 leave_policy.pdf가 낮은 순위로 근거에 섞여 들어옴(정답 문서보다는 항상 아래 순위지만 완전히 사라지진 않음). 완전히 없애려면 ES 인덱스에 `nori` analyzer를 붙이는 별도 작업이 필요 — 지금은 하지 않음.

### 4.0.1 근거 인용에 실제 매칭 부분 하이라이트 추가 (search-service, chat-service, frontend, 2026-08-27)
- 위 이슈를 고치면서 함께 요청받은 기능: 근거 스니펫에서 실제로 어느 부분이 매칭됐는지 표시.
- `HybridSearchService`의 키워드 검색에 ES `highlight`(`numberOfFragments(0)`로 필드 전체를 매칭 부분만 마커로 감싸 반환)를 추가하고, 실제 문서 텍스트에 나타날 일이 없는 제어문자(SOH/STX)를 마커로 씀 — `answer_source.snippet`엔 이 마커가 그대로 저장되고(스키마 변경 없이 기존 컬럼 재사용), `ChatService.buildSystemPrompt()`는 LLM에 넘기기 전에만 마커를 제거함(LLM 컨텍스트에 불필요한 제어문자가 들어가지 않도록).
- 프론트(`ChatView.vue`)는 스니펫을 **먼저 HTML 이스케이프한 뒤** 마커만 `<mark>`로 치환해서 `v-html`로 렌더링 — 순서를 바꾸면(마커 치환 후 이스케이프) 문서 원문에 `<`/`>`가 있을 때 XSS로 이어질 수 있어 반드시 이 순서를 지켜야 함.
- 하이라이트가 실제로 위 4.0의 오탐 사례("다음 해")를 그대로 보여줘서, 왜 엉뚱한 문서가 근거로 딸려왔는지 사용자가 바로 눈으로 확인할 수 있게 됐다는 부수 효과도 있음.

### 4.1 MinIO(S3) 요청이 AWS SDK에서만 무한 대기 (document-service, 가장 오래 걸린 삽질)
- **증상**: `S3Client.headBucket()` 등 AWS SDK v2 호출이 타임아웃, 그런데 curl·AWS CLI·Python botocore는 동일 엔드포인트에 즉시 성공.
- **원인**: 로컬에 떠 있던 Jupyter 커널이 ZMQ 채널 5개(shell/iopub/stdin/control/hb)로 9000~9004 포트를 통째로 점유 — MinIO 기본 포트(9000/9001)와 충돌. curl은 뭐가 응답하든 그럴듯하면 넘어가서 문제를 못 느꼈던 것.
- **해결**: MinIO 포트를 9100/9101로 변경(`infra/docker-compose.yml`).
- **다음에 의심할 순서**: SDK 버전 → 체크섬/청크 인코딩 옵션 → IPv4/IPv6 순으로 의심하기 전에, `lsof -i -P -n -a -p <pid>`로 포트 점유 프로세스부터 확인할 것.

### 4.2 ES 클라이언트/서버 버전 불일치 (search-service)
- **증상**: Boot 4.1.1의 `co.elastic.clients:elasticsearch-java`가 9.4.5로 고정, 서버는 8.15.0로 띄워서 호출이 이상하게 실패.
- **해결**: ES 서버 이미지도 9.4.5로 맞춤. 로컬 볼륨이 비어 있어 재색인 없이 그냥 새로 띄우면 됐음.
- **적용 범위**: Boot 버전을 올릴 때마다 ES 클라이언트 버전이 따라 바뀔 수 있음 — `./gradlew dependencies --configuration compileClasspath | grep elasticsearch-java`로 먼저 확인.

### 4.3 색인은 되는데 `_source`에 `embedding` 필드가 안 보임 (search-service)
- **증상**: Java 클라이언트, curl, Python 순수 HTTP 호출 전부 동일하게 `dense_vector` 필드가 `_source` 조회에서 빠짐.
- **원인**: 서버(ES 9.4.5) 쪽 동작으로 확인(클라이언트 버그 아님) — 세 가지 방식으로 교차 검증.
- **판단**: 임베딩은 색인 시점에 벡터 인덱스 구조를 만드는 데만 쓰이고, 검색 시점엔 쿼리 텍스트를 매번 새로 임베딩해서 비교하므로 저장된 값을 다시 읽을 일이 없음 → 실제 기능에 영향 없다고 판단하고 원인 추적을 중단, 대신 "차원 불일치 시 400", "kNN 결과가 맞는지"로 검증 기준을 바꿔서 확인.

### 4.4 게이트웨이가 다른 사용자의 로그인 쿠키를 재전송 (보안 버그, api-gateway)
- **증상**: A가 게이트웨이로 로그인 → 완전히 쿠키 없는 B의 요청이 A의 로그인 데이터를 그대로 돌려받음.
- **원인**: `spring-cloud-starter-gateway-server-webmvc`가 프록시에 쓰는 `RestClient`가 Apache HttpClient5로 자동 구성되는데, 기본값이 **쿠키 저장소를 켠 채** 만들어짐 — 게이트웨이 프로세스 자신이 `Set-Cookie`를 저장했다가 무관한 다음 요청에 재전송.
- **해결**: `config/GatewayHttpClientConfig.java`에 `HttpClients.custom().disableCookieManagement()`로 만든 `ClientHttpRequestFactory` 빈을 등록.
- **일반화**: Spring Cloud Gateway **Server MVC**(WebFlux 아님) 쓰는 곳이면 어디든 이 기본 동작을 의심할 것 — 하드닝이 아니라 기본값 자체의 데이터 유출 버그임.
- **발견 경로**: "인증된 경로 확인 후 반드시 인증 안 된 경로도 테스트" 습관 덕분에 발견됨(해피 패스만 봤으면 놓쳤을 버그).

### 4.5 `@LoadBalanced RestClient.Builder`가 Eureka 클라이언트를 순환 참조로 물고 들어감 (user-service)
- **증상**: 서비스 간 호출(user→auth)을 위해 `@Bean @LoadBalanced RestClient.Builder`를 등록했더니 부팅 자체가 순환 참조로 실패.
- **원인**: 이 빈이 Boot의 기본 `RestClient.Builder`를 대체(`@ConditionalOnMissingBean`)해버려서, Eureka 클라이언트 자신의 내부 HTTP 호출까지 로드밸런서를 타게 되고 아직 뜨지도 않은 자기 자신을 discover하려 함.
- **해결**: `DiscoveryClient.getInstances(serviceId)`로 인스턴스를 직접 조회한 뒤 `RestClient.create()`로 호출. 이후 모든 서비스 간 호출(document, search, chat)에서 동일 패턴 재사용.

### 4.6 Eureka(discovery-service) 재기동만으로는 전체 복구 안 됨
- **증상**: 장시간 로컬 세션에서 discovery-service가(메모리 압박 추정) 혼자 죽음. 재기동해도 이미 떠 있던 다른 서비스들은 `Connection refused`를 반복하다 재시도를 포기한 채 스스로 재등록하지 않음.
- **해결**: discovery-service 재기동 후 **나머지 서비스도 전부 재기동**해야 함. `curl http://localhost:8761/eureka/apps`로 등록 인스턴스 수(정상 6개)를 확인하는 걸 상시 체크포인트로 삼음.

### 4.7 오래 떠 있던 서비스가 stale IP로 Eureka에 등록됨 (api-gateway → auth/user-service)
- **증상**: 게이트웨이 → auth/user-service 호출만 "Network is unreachable", 그 외 서비스 간 호출과 직접 curl은 정상.
- **원인**: 맥의 활성 네트워크 인터페이스가 세션 중간에 바뀌었는데, 오래 떠 있던 두 서비스만 예전 IP로 Eureka에 등록된 채 남음.
- **해결**: 해당 서비스 재기동 → 현재 IP로 재등록.
- **패턴 인식 포인트**: "오래 켜둔 서비스로부터의 호출만 실패, 새로 뜬 서비스는 멀쩡, 직접 호출은 됨" 조합이면 stale IP부터 의심.

### 4.8 Boot 4.1 관련 마이그레이션 이슈 (document-service에서 처음 발견, 전 서비스 공통)
- `Health`/`HealthIndicator`가 `org.springframework.boot.actuate.health` → `org.springframework.boot.health.contributor`(신설 `spring-boot-health` 모듈)로 이동. 옛 패키지는 컴파일 에러.
- Kafka `HealthIndicator`가 기본 제공되지 않음(매 헬스체크마다 `describeCluster()` 비용 때문) — `KafkaHealthIndicator`를 직접 작성해 재사용(document-service, search-service 동일 코드).
- 반대로 Elasticsearch는 Boot가 기본 제공 — 별도 작성 불필요.

### 4.9 Spring Initializr Gradle 프로젝트 생성이 서버에서 500
- **해결**: Maven으로 생성 → Maven 파일 제거 → `loginauth-springboot` 스타일로 `build.gradle` 수동 작성(BOM import, dependency-management 플러그인 아님) → `gradle wrapper --gradle-version 9.0.0`.
- **부작용**: Spring Initializr가 만든 `.gitignore`는 Maven 전제라 `target/`만 무시하고 `.gradle/`/`build/`가 없음 — Gradle로 전환한 뒤 `git add` 전에 반드시 `.gitignore`를 Gradle용으로 다시 써야 함(두 번 실제로 걸림 — document-service, search-service).

### 4.10 `kill -9`로 재기동한 직후 Kafka 컨슈머가 메시지를 잠깐 못 받음
- **원인**: `kill -9`는 Kafka에 정상적인 "leave" 요청을 보내지 않아 컨슈머 그룹이 rebalancing 상태로 남고, 세션 타임아웃(약 10~30초)이 지나야 안정화됨.
- **판단 기준**: `kafka-consumer-groups.sh --describe --group <id>`에서 `LAG > 0` 또는 rebalancing 경고 → 코드 문제가 아니라 그냥 안정화를 기다리거나 이벤트를 재발생시키면 됨.

### 4.11 코드 변경 없이 `NoClassDefFoundError` 발생
- **원인**: `build/classes`가 스테일 상태로 남음(여러 JVM을 오래 띄워둔 세션에서 발생).
- **해결**: `./gradlew clean bootRun`. 소스가 정상인데 이런 에러가 나면 빌드 산출물부터 의심.

### 4.12 백엔드 재시작 후 "브라우저에서만" 500, curl은 정상
- **증상**: 오래 떠 있던 auth/user-service JVM이 어느 시점부터 브라우저(axios/fetch, Vite 프록시 경유) 요청에만 500, 동일 URL로 curl하면 200.
- **대응**: Vite 재시작은 무관, **해당 백엔드 서비스를 재기동하면 즉시 해결**. 원인(브라우저의 지속 연결과 관련된 stale keep-alive 커넥션으로 추정)을 더 파기보다 재기동이 빠르고 확실해서 그쪽을 택함.

### 4.13 신규 컨트롤러 추가 시 게이트웨이 라우트 누락
- **증상**: auth-service에 `CompanyController`(`/api/companies/**`)를 추가했는데 게이트웨이에 대응 라우트를 안 넣어서 프론트에서 404.
- **해결**: `application.yml`에 라우트 추가.
- **체크리스트화**: 새 컨트롤러를 만들 때마다 게이트웨이 라우트 추가 여부를 확인.

### 4.14 claude-in-chrome 브라우저 자동화 관련 팁 (개발용 참고, 앱 버그 아님)
- 픽셀 좌표 클릭은 레이아웃이 미세하게 바뀔 때마다 어긋남 → `read_page`/`find`로 얻은 요소 `ref` 기반 클릭/입력이 대체로 더 안정적.
- 그런데 특정 `el-button`(submit)에서는 ref 클릭도 무반응(네트워크 요청도 안 나가고 콘솔 에러도 없음)인 경우가 있었음 → `javascript_tool`로 `document.querySelectorAll('button')`에서 텍스트로 찾아 `.click()`을 직접 호출하니 정상 동작. 자동화 도구의 합성 클릭 전달 문제였고 실제 앱 버그는 아니었음.
- `el-tag` 등 Element Plus 컴포넌트가 화면에 안 보이는 것처럼 캡처될 때, mount 시 `zoom-in-center` 트랜지션 때문에 스크린샷 타이밍에 `width:0`으로 잡힐 수 있음 → 1~2초 뒤 재확인하거나 `getBoundingClientRect()`로 직접 확인할 것(같은 문제로 세 번 헛다리 짚었던 패턴).

## 7. 알려진 한계 / 남은 작업

- **HWP 텍스트 추출 미지원** — 원본 저장/다운로드는 되지만 검색 색인 대상에서 빠짐(성숙한 자바 HWP 파서 부재).
- **문서 보안등급별 다운로드 제한(REQ-F-008) 없음** — 문서에 등급 필드 자체가 아직 없음.
- **회사 선택 UI 없음** — 예외 가입은 `company_id=1`로 고정, 실제로는 신청 시 회사 지정 또는 관리자 배정이 필요.
- **LLM/임베딩이 전부 로컬 Ollama** — OpenAI/Claude API 키가 생기면 `EmbeddingClient`/`ChatClient` 구현체를 하나씩 추가하고 활성 빈만 바꾸면 되도록 설계는 되어 있지만 실제 전환은 아직 안 함.
- **한국어 형태소 분석기(Nori) 미적용** — ES 인덱스가 표준 analyzer를 쓰고 있어, 조사가 붙은 짧은 한글 단어가 다른 단어와 우연히 토큰이 겹치는 약한 오탐이 가능함(4.0 참고 — 순위는 항상 정답 문서보다 낮지만 완전히 사라지진 않음). `nori` analyzer 적용은 별도 작업.
- **순수 패러프레이즈(키워드 완전 비겹침) 질문은 결과 없음으로 처리될 수 있음** — 4.0에서 관련성 없는 결과를 걸러내려고 "키워드 매칭이 하나도 없으면 벡터 단독으로는 결과를 안 준다"로 바꾼 트레이드오프. 이 코퍼스/임베딩 조합에서는 벡터 유사도만으로 관련성을 신뢰할 수 없다는 걸 실측으로 확인하고 내린 선택(recall보다 precision 우선).
